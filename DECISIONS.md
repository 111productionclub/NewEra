## D-01 · Стек · 2026-10-17
Вопрос: на чём строим NewEra и будущие студийные проекты.
Варианты: A) чистые HTML/CSS/JS; B) Vite + vanilla JS; C) Astro; D) Next.js + React + TypeScript.
Решение: Next.js (App Router) + React + TypeScript + Tailwind CSS; анимации GSAP / Motion (+ Lenis для скролла, Three.js при необходимости); бэкенд позже на Django + DRF + Postgres; деплой на Vercel.
Почему: студия хочет делать сильные проекты, поэтому нужны стандартные профессиональные инструменты, на которых можно взять любой заказ. Промежуточный этап на vanilla JS пропускаем. Владелец проекта любит Django, поэтому он остаётся бэкендом.
Отброшено: vanilla/Vite (учит основам, но не стек для заработка), Astro (хорош для контента, но уже, чем нужно студии).

## D-02 · Структура репозитория · 2026-10-17
Вопрос: как организовать код фронта и будущего бэкенда в условиях команды из 3 человек и 2 проектов.
Варианты: A) один репозиторий на проект с папками frontend/ и backend/; B) отдельные репозитории под фронт и бэк; C) общий монорепо студии (Turborepo/Nx).
Решение: A. Один репозиторий на проект, внутри frontend/ и backend/. Общий код между проектами пока не выносим. Пакетный менеджер pnpm, хостинг кода на GitHub, main защищён, работа через feature-ветки и pull request с ревью.
Почему: команда небольшая, проекты независимы (свои релизы, заказчики, доступы). Инструменты монорепо окупаются при 5+ проектах с общим кодом. Если появится заметное дублирование, вынесем общий пакет (например studio-ui).
Отброшено: B (лишний оверхед на два репозитория одного продукта), C (избыточно для 2 проектов).

## D-03 · Git, GitHub и правила веток · 2026-10-17
Вопрос: где хранить код, как вести ветки и как защитить main.
Решения:
- Код хранится в GitHub Organization студии (репозиторий принадлежит студии, а не одному человеку).
- Модель веток: trunk-based. main всегда рабочий, от него отходят короткие ветки feat/..., fix/..., chore/..., которые вливаются через pull request.
- Коммиты по Conventional Commits (feat:, fix:, chore:), из истории удобно собирать changelog и таймлайн для видео.
- Ветка по умолчанию называется main (git init -b main).
- Добавлен .gitignore (.DS_Store, node_modules, .next, .env, .env.local).
- Репозиторий сделан публичным, на main включён ruleset (PR перед слиянием, блокировка force push).
Что произошло по дороге: создали приватный репозиторий, но на бесплатном плане организации защита веток для приватных репозиториев недоступна (нужен платный GitHub Team). Выбрали публичный репозиторий: NewEra портфолио-проект, секретов в истории нет, код можно показывать в видео. Для клиентских проектов потом выбираем между платным планом и командной дисциплиной.
Отброшено: Git Flow (избыточен для команды из 3 человек), личный аккаунт (проект привязан к одному человеку).

## D-04 · Каркас фронтенда · 2026-10-17
Вопрос: как создать проект Next.js и что делать со старым прототипом.
Решения:
- Старый статичный прототип перенесён в legacy/ (для сравнения «было → стало» в видео, позже удалим).
- Проект создан командой pnpm create next-app в папке frontend/.
- Настройки: TypeScript, ESLint, Tailwind CSS, папка src/, App Router, алиас импорта @/*. React Compiler и Cache Components отключены.
- Версии на момент создания: Next.js 16.4.2, React 19.3.0, pnpm 12.14.0 (зафиксирован в package.json через packageManager, чтобы у всех троих была одна версия).
Почему: src/ отделяет код приложения от конфигов, алиас убирает длинные относительные пути. Cache Components и React Compiler для лендинга с четырьмя товарами не нужны, усложняют обучение; включим позже, когда появятся данные из Django.
Проверка: pnpm dev, на localhost:3000 открывается стартовая страница Next.js.

## D-05 · Структура frontend/src/ · 2026-10-17
Вопрос: как разложить код приложения по папкам.
Решение:
- src/app/ — маршруты App Router (layout.tsx, page.tsx, products/[slug]/page.tsx).
- src/components/ — переиспользуемые части интерфейса, разбиты по темам: layout/ (Header, Footer), product/ (ProductCard, ProductGallery, SizeSelector).
- src/data/products.ts — данные товаров (позже заменятся на запросы к Django API).
- src/lib/ — утилиты (например formatPrice).
- src/types/product.ts — тип Product.
Принципы:
- Данные не живут в компонентах: компонент получает товар через пропсы и не знает, откуда он пришёл (файл или Django).
- Тип Product сразу делаем таким, каким его потом отдаст Django, чтобы при подключении API менялся только источник данных.
- Server Components по умолчанию, "use client" только там, где нужна интерактивность (галерея, выбор размера).
Почему: минимальная структура по смыслу, без лишних слоёв; растёт вместе с проектом.

## D-06 · Покупка через корзину и диалог ВК · 2026-10-17
Вопрос: как покупатель оформляет заказ, если оплаты и бэкенда пока нет.
Варианты:
- Ссылка на ВК прямо в карточке товара (текущий этап).
- Корзина на сайте, оформление через сообщение в ВК с готовым текстом заказа.
Решение: сначала ссылка на ВК в карточке. Позже добавляем корзину; по кнопке «Оформить» сайт копирует текст заказа («Хочу купить: bomber, размер M») в буфер обмена и открывает диалог сообщества (vk.me/...).
Почему: ВК не позволяет подставить текст сообщения через ссылку, поэтому копируем его в буфер обмена. Вариант с ref-меткой и ботом требует настройки в ВК, его оставляем на потом.
Следствия: корзина и выбор размера станут клиентскими компонентами ("use client"), состояние корзины хранится в localStorage. Scope проекта расширяется: корзина добавляется вторым этапом, после страницы товара.

## D-07 · Сетка товаров и страница товара · 2026-10-18
Вопрос: как выводить фото в сетке и на странице товара, чтобы вёрстка не прыгала и не грузились лишние мегабайты.
Варианты:
- Картинки с фиксированными width и height (как в первой версии карточки).
- Картинки через next/image с fill и sizes внутри обёртки с заданными пропорциями.
Решение: второй вариант. Обёртка получает relative и aspect-[...], внутри Image с fill, sizes и object-cover. Сетка карточек на CSS Grid с брейкпоинтами (1 колонка → 2 → 4, mobile-first). Страница /products/[slug] остаётся серверной: товар ищется по slug, для несуществующего адреса вызывается notFound(), список адресов отдаёт generateStaticParams, поэтому страницы собираются заранее при сборке.
Почему: пропорции задаёт обёртка, значит место под фото резервируется до загрузки. Через sizes Next отдаёт файл подходящего размера под экран. Фиксированные width и height не растягиваются по колонке.
Что поймали по пути:
- Несколько картинок с fill в одной обёртке накладываются друг на друга, обёртка нужна на каждую картинку.
- В images лежат файлы разного назначения: одно большое фото и квадратные превью. Выводить их одинаково нельзя, большое фото берётся как images[0], остальные как миниатюры через slice(1).
Следствия: галерея и выбор размера потребуют "use client" (useState). Решение: страница остаётся серверной, клиентскими станут только отдельные компоненты ProductGallery и SizeSelector.

## D-08 · Корзину откладываем, покупка через буфер и диалог VK · 2026-10-20
Вопрос: делать ли корзину в рамках дедлайна (на всё про запас два дня).
Варианты:
- Корзина со списком, счётчиком в хедере и localStorage (D-06).
- Без корзины: кнопка «Купить» на странице товара копирует текст заказа и открывает диалог сообщества VK.
Решение: второй вариант. Выбор размера и кнопка «Купить» живут в одном клиентском компоненте, выбранный размер поднимается из SizeSelector в родителя. Текст заказа: «Хочу купить: <товар>, размер <размер>». Ссылка на диалог VK одна на весь сайт, лежит в константе, а не в данных товара.
Почему: оформление заказа всё равно идёт через ВК-сообщение, корзина не нужна для запуска. Она самая объёмная часть и самая рискованная по срокам.
Следствия: D-06 остаётся в силе как план на второй этап, но корзина уходит за дедлайн. Тип Product не меняется.

## D-09 · Статический экспорт · 2026-10-20
Вопрос: как собирать сайт, если он будет жить на хостинге клиента, а не на Vercel.
Варианты:
- Обычная сборка Next.js, нужен сервер с Node.js.
- Статический экспорт (output: "export"): сборка даёт папку out/ с готовыми HTML, CSS и JS, которую можно положить на любой хостинг.
Решение: статический экспорт с images.unoptimized: true.
Почему: на обычном хостинге нет Node.js, а сайт целиком состоит из данных, известных на этапе сборки (products.ts), поэтому все страницы товаров собираются заранее через generateStaticParams. Встроенная оптимизация next/image требует работающего сервера, поэтому её отключаем: картинки отдаются как есть, значит их нужно сжимать вручную до добавления в public/img.
Следствия: при подключении Django API придётся либо пересобирать сайт при смене товаров, либо вернуться к обычной сборке с сервером.

## D-11 · Шрифты как в прототипе · 2026-10-21
Вопрос: чем заменить шрифт Geist/Arial, чтобы сайт выглядел как legacy.
Варианты:
- Системный рукописный стек из прототипа (Lucida Handwriting, Segoe Script, Comic Sans MS, cursive).
- Подключить один рукописный шрифт через next/font, одинаковый на всех устройствах.
Решение: основной и «рукописный» (Ink Free) шрифты остаются системным стеком, как в прототипе; статус на карточке тоже рукописным (Pixelify Sans был подключён и убран как ненужный). Курсив, letter-spacing 0.05em и утилита text-stroke (утолщение текста) заданы в globals.css.
Почему: так вид совпадает с эталоном без лишних файлов. Минус: Lucida Handwriting и Ink Free есть не везде (на Android сработает общий cursive).
Следствия: если клиенту нужен одинаковый вид на всех устройствах, заменим системный стек на шрифт через next/font в одном месте (layout.tsx и --font-main).

## D-12 · Карточка с текстом поверх фото · 2026-10-21
Вопрос: как повторить карточку из прототипа, где название, цена и статус лежат на фото, если у фото разная яркость, а флаги оформления в данные не добавляем (D-05).
Варианты:
- Флаг dark в типе Product (белый или чёрный текст).
- Всегда белый текст на тёмном градиенте снизу.
Решение: второй вариант. Карточка целиком ссылка, градиент from-black/60 внизу, статус пиксельным шрифтом справа сверху, размер текста от ширины карточки (cqw). Статус «5 Remaining» не делаем: нет базы с остатками, для few-left выводим «Few left».
Почему: данные остаются фактами, текст читается на любом фото.
Следствия: если появится бэкенд с остатками, текст статуса возьмём из данных.

## D-13 · Страница товара как в прототипе · 2026-10-21
Вопрос: как привести страницу /products/[slug] к виду legacy.
Решение: раскладка на Tailwind с брейкпоинтами прототипа (640, 1100, 1700px): на широком экране в ряд «Назад», галерея, инфо; на узком друг под другом. Почему: прототип утверждён заказчиком как эталон вида; единые радиусы дают цельный вид.
Следствия: недоступные размеры (диагональ в прототипе) не делаем, в данных их нет.

## D-15 · Фильтр каталога по категориям · 2026-10-21
Вопрос: как добавить фильтры в каталог, если в прототипе их нет, а товаров пока мало.
Варианты:
- Фильтр по размеру или наличию.
- Фильтр по категории товара.
Решение: поле category в Product (top, bottom, accessories; это факт, D-05 не нарушен). Подписи в src/data/categories.ts. Над сеткой заголовок «Каталог ↓» как кнопка: клик сворачивает и разворачивает таблетки категорий (по умолчанию свёрнуто); выбранная категория видна в заголовке. Почему: категория понятна покупателю и растёт вместе с каталогом; таблетки в стиле кнопок размеров вписываются в дизайн; свёрнутый блок не ломает чистый вид прототипа.
Следствия: пустая категория (пока «Аксессуары») показывает «Скоро здесь появятся новые вещи». Новая категория добавляется в тип ProductCategory и в CATEGORY_LABELS.

## D-17 · Бэкенд для админки товаров · 2026-10-21
Вопрос: как дать администратору менять товары и загружать фото без правки кода.
Варианты:
- Своя админка на фронтенде.
- Django: встроенная админка и REST API (план из CLAUDE.md).
Решение: backend/ на Django + DRF + SQLite (позже Postgres). Модели Product и ProductImage (фото загружаются через админку в media/). API только на чтение: /api/products/ и /api/products/<slug>/, ответ совпадает с типом Product из frontend/src/types/product.ts (id, slug, name, price, category, status, images, sizes, description, vkUrl), скрытые товары в API не попадают. Размеры хранятся строкой через запятую, описание текстом (строка = пункт).
Почему: встроенная админка Django даёт форму с загрузкой фото из коробки; формат API заранее совпадает с типом на фронте (D-05), поэтому при подключении меняется только источник данных.
Следствия: фронтенд пока читает src/data/products.ts. Как именно подключить API к статическому сайту (D-09), решено не было: пересборка сайта при изменении товаров, либо загрузка данных в браузере (тогда страницы товаров перестают собираться заранее). Это отдельное решение (следующий D-XX).

## D-18 · Схема развёртывания на сервере · 2026-10-21
Вопрос: как разместить сайт и Django-бэкенд на сервере, где 80/443 уже занимает Caddy другого проекта (sleng).
Варианты:
- Встроить наш бэкенд и статику в compose проекта sleng.
- Свой compose проекта newera (бэкенд + nginx) в сети sleng, а Caddy sleng получает один блок для newerastore.ru.
Решение: второй вариант. Контейнеры newera-backend (Django + gunicorn, SQLite в томе) и newera-web (nginx: статика сайта, /media, /static, прокси /admin и /api). Caddy проксирует домен на newera-web. Файлы в deploy/ и backend/Dockerfile, инструкция в deploy/README.md (без реальных адресов и учётных данных сервера).
Почему: проект sleng и его база не затрагиваются, правка только добавляет блок в Caddyfile (с бэкапом, validate и reload без остановки); HTTPS выдаёт уже работающий Caddy.
Следствия: DNS домена должен указывать на сервер до получения сертификата. SQLite достаточно для одного администратора, при росте переходим на Postgres. Подключение фронтенда к API остаётся отдельным решением.

## D-19 · Сжатие фото товаров · 2026-10-25
Вопрос: сайт тормозит, потому что фото из админки отдаются оригиналами (с телефона по 3–10 МБ), а при `output: "export"` Next.js сам картинки не сжимает (`images.unoptimized`).
Варианты:
- Сжимать при сборке фронта (`next-image-export-optimizer`).
- Внешний CDN с ресайзом на лету.
- Сжимать на бэкенде при загрузке в админку и отдать фронту готовые размеры.
Решение: третий вариант. При загрузке Django (Pillow) делает рядом с оригиналом три WebP: `_400` (миниатюры), `_800` (карточки), `_1600` (страница товара), длинная сторона, без обрезки, качество 82, с поворотом по EXIF и сохранением прозрачности. API отдаёт `_1600`, свой загрузчик `next/image` (`frontend/src/lib/imageLoader.ts`) подставляет меньший размер по ширине из `srcset`, браузер скачивает нужный под экран. Старые фото обрабатывает команда `manage.py optimize_images`.
Почему: фото приходят из админки, а не из `public/`, поэтому оптимизатор при сборке до них не дотягивается; CDN добавляет сервис и расходы. Тип `Product` и формат API не меняются (`images: string[]`), поэтому ничего на сервере, что читает API, не ломается. Оригиналы остаются, размеры можно пересоздать (`--force`).
Следствия: размеры заданы в двух местах (`backend/products/images.py` и `imageLoader.ts`), менять вместе. Лимит загрузки поднят до 30 МБ на фото и 100 МБ на запрос в nginx. HEIC с айфона Pillow не открывает: такие фото сохранять в JPEG (или позже добавить `pillow-heif`).

## D-20 · Сайт берёт товары из Django API при сборке · 2026-10-25
Вопрос: как подключить фронтенд к админке, если сайт статический (`output: "export"`), а товары меняются в Django.
Варианты:
- Запрашивать API из браузера на каждом заходе (клиентские компоненты).
- Перейти на серверный рендер Next.js (отдельный Node-процесс на сервере).
- Брать товары из API во время сборки и пересобирать сайт после изменений в админке.
Решение: третий вариант. `src/data/getProducts.ts` читает `PRODUCTS_API_URL/api/products/`, главная, страницы товаров (`generateStaticParams`) и sitemap берут товары через него. Без переменной (локальная разработка) используется заглушка `src/data/products.ts`. На сервере сборку запускает `deploy/rebuild-site.sh` внутри сети Docker. Абсолютные адреса фото API превращаются в пути `/media/...`, их отдаёт nginx.
Почему: сайт остаётся статическим (быстрый, без лишнего процесса на сервере), а компоненты по-прежнему получают `Product` через пропсы (D-05), меняется только источник данных. Эти правки раньше жили только на сервере вне git, из-за чего ломались обновления.
Следствия: изменения в админке видны на сайте только после `rebuild-site.sh`. Сборка падает, если API недоступен, и в этом случае старая версия сайта остаётся на месте. Для сборки в `DJANGO_ALLOWED_HOSTS` нужен `newera-backend`.
